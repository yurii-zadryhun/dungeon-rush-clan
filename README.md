# Dungeon Rush · Clan War Archive

Private, lightweight clan-war dashboard. **NestJS + Fastify, React + Vite, SQLite/Kysely**, one process in production. Source code is maintained directly on `master`.

## Features

- Integrated **Clan Wiki** with 29 original Ukrainian/English guides, plus an optional source-grounded AI Q&A assistant.
- Responsive wiki reader with section navigation, full-text search, category filtering, local bookmarks, related articles and shareable hash URLs (e.g. `#/wiki/war-calendar`).
- Wiki content is versioned in `web/src/wiki/data/` and requires no additional server schema, third-party renderer or database migration. Clan member accounts use their existing saved language preference.

- Fully generated Tuesday–Sunday UTC war timeline; Mondays have no war.
- Separate rankings (from Sunday 00:00 UTC) and **final** war results (from Monday 00:00 UTC).
- Cloud Vision OCR for up to 10 weekly leaderboard screenshots + one final-result screenshot.
- Editable review of ranks, names, points, opponent, six daily winners and MVPs; duplicate ranks reconciled.
- Player entry/exit detection based on the latest _chronological_ imported weekly ranking (including 0-point members).
- Rolling weighted leaderboard (75/25 by default), configurable minimum points, all-time average and latest-war widgets.
- Multiple owner accounts; owners can invite other owners or administrators. Administrators can invite **members only**, including through the reusable group link.
- Account management lives at `#/users` for owners and administrators (no access for members).
- Individual username/password accounts, single-use and reusable Member-only invitations, revocation and server-side rolling sessions.
- Account profile with in-game nickname/password changes. A stable player link preserves historical rankings when a nickname changes; MVP texts are updated too.
- Sticky mobile-safe header, full-player leaderboard expansion, and a horizontally paged war timeline.
- SQLite WAL, transactional imports, bounded OCR requests, local OCR cache; no Redis or runtime frontend build.

## Wiki AI assistant

The Wiki includes an optional bilingual Q&A assistant at `#/wiki/ask`, powered by the hosted `gemma-4-31b-it` model through the Gemini API. It reads **only relevant wiki sections**: a local bilingual retrieval index is rebuilt automatically from the existing guides before `dev`, `check`, `test` and `build`.

- Server-only setting: `GEMINI_API_KEY` in the application's private `.env` file. If missing, the assistant clearly shows as unavailable; the rest of the site works normally.
- **GitHub Actions secrets are not automatically available to the running application.** A repository secret alone does not configure production. Provision the key in `$APP_PATH/.env` on the DigitalOcean server and restart PM2 with `--update-env`. Do not add it to `VITE_*` variables, deployment tarballs, static assets or source files.
- Keep the Google AI Studio project on **Free Tier without billing**. The code has no paid fallback: only the free-tier Gemma 4 31B model is called.
- Rate limiting is per account and global: 4 requests/minute and 80/day per user, 20/minute and 3,000 per rolling 24 hours globally; conservative estimated input token budget of 11,500/minute and maximum 3 simultaneous calls.
- The server caches duplicate questions for 6 hours, holds only the last exchange in context, limits output to 384 tokens and sends up to four relevant wiki fragments rather than the full corpus.
- Source links are selected and validated locally; the model cannot invent wiki URLs in the response.
- Questions and wiki excerpts are sent to Google; no account names, emails, passwords, historical clan roster or private chats are included. Do not ask for sensitive personal information.
- If the API key is missing, revoked, exhausted or the provider is unavailable, the assistant fails clearly without affecting the wiki. No extra SQL tables or runtime GPU are required.

The index is generated by `npm run wiki:index` into the ignored `server/src/ai/wiki-index.json`, then compiled into the server bundle. Do not edit generated data by hand.

## Requirements

- Node.js 22+, npm, HTTPS reverse proxy for production, enough disk space for SQLite and OCR cache.
- A Google Cloud project with **Cloud Vision API** enabled and an API key authorized to call it. Set API restrictions for Cloud Vision; keep the key on the server. Google Cloud billing/free tier conditions are account-dependent.
- Port 3000 by default; can be changed.

## Install

```sh
npm install
cp .env.example .env

openssl rand -hex 24          # paste as BOOTSTRAP_TOKEN in .env
# configure APP_ORIGIN and GOOGLE_VISION_API_KEY
npm run check
npm test
npm run build
npm start
```

Open the application and enter the one-time setup token to create your owner account. After setup, remove `BOOTSTRAP_TOKEN` from the server environment and restart. Back up `data/clan.sqlite` before upgrades. Legacy TOTP secrets are removed by an automatic migration; existing passwords and sessions are retained.

Do not commit `.env`, `data`, API keys or invitation links. Secrets and invitations should only be shared privately.

For local frontend hot reload, use `npm run dev`; Vite proxies API traffic to the NestJS process. Set `APP_ORIGIN` appropriately for the production origin, without a trailing slash. Enable HTTPS and `NODE_ENV=production` in production, and set `TRUST_PROXY=1` only behind a trusted reverse proxy that overwrites proxy headers. Cookies are HttpOnly + SameSite Strict + Secure in production.

## Roles

| Role | View | Import/settings | Invite | Revoke accounts |
| --- | --- | --- | --- | --- |
| Owner (multiple allowed) | Yes | Yes | Owner/Admin/Member | Yes, except themselves and the last owner |
| Admin | Yes | Yes | Member only | No |
| Member | Yes | No | No | No |

Owners and admins can manage the reusable Member-only group link. Password changes are separate from nickname edits and require the current password. Renaming preserves the historical player ID and updates MVP text.


## Business rules

- War begins **Tuesday 00:00 UTC**. Day 1–6 points: `[1,2,2,2,2,4]`, sum 13. Monday is off.
- Weekly player ranking is available from **Sunday 00:00 UTC**, but the war result is only final on **Monday 00:00 UTC**. A war may be partially imported. The two sections each allow **one first-time import**; editing/re-import is intentionally out of scope.
- Import confirmation is atomic. Older-war imports cannot overwrite current clan membership: activity is derived from the newest chronological imported roster.
- User identity is stable SQLite ID. Normalized names enable exact auto-match; OCR review lets the admin link a misread name to an existing player. Renaming and aliases are deferred.
- Calculated score uses the newest imported rankings, **not future/empty weeks**. Default weights 75%/25%; configured weights are normalized when fewer weeks exist. Missing players score zero for the missing week.
- All-time ranking uses mean weekly points across appearances; inactive players remain listed but dimmed.
- OCR responses are cached by SHA-256 of the screenshot bytes under `data/ocr-cache`, so retrying the identical image does not repeat the paid OCR request. The cache holds OCR text and player names: protect and back it up only if necessary.
- The Google OCR geometry parser is designed against supplied game screenshots and has offline tests. Since Vision results depend on image quality and font, **verify every field** during review.

## Cloud Vision 403

If an import fails with Google Cloud Vision HTTP 403, the API now includes the original Google error reason in the response (never the API key). Verify the Cloud Vision API is enabled in the Google Cloud project, billing is active if required, and the API key is allowed to call Cloud Vision from the **backend**. Browser HTTP referrer restrictions are unsuitable for a server-to-server API key; use Cloud Vision API restrictions and an appropriate server IP restriction when possible. Do not publish the key in frontend code.

## Future MySQL migration

Keep business logic in NestJS services and SQL access in DB/repositories. The Kysely query API is dialect-independent; schema and SQLite-specific conflict handling must be migrated to MySQL. Do not share the SQLite file over a network filesystem.
